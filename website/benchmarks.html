Benchmarks

← back to angelX

Three harnesses — angelX, OpenCode and oh-my-pi — ran the same polyglot-v1 suite: 136 repository-repair tasks across JavaScript, Python, Rust and C++, each graded by its own tests. Two models ran the suite: DeepSeek V4.1 Flash with thinking off, and GLM-5.3-Flash at its lowest accepted thinking level. Every attempt ran in a fresh environment under a 600 s wall-clock cap. Nothing below is self-reported: pass, fail and token counts come from the evaluator’s traces.

The six views on this page are the same run seen from six angles — score, cost, latency and cache behaviour. Read individually they answer one question each; read together they describe the shape of a harness rather than a single number. Each figure carries a note on how to read it, including the parts that flatter nobody.

The race to 136

Solved attempts against cumulative agent timeEach line steps up once when a task passes. Higher and further left is strictly better: more tasks solved in less wall-clock time. Flat stretches are failed attempts and retries.

How to read it. The vertical axis counts solved tasks, 0–136 across the suite. oh-my-pi’s DeepSeek run ends at 59 because it hit its 200M-token budget cap, so compare its slope rather than its height. The horizontal axis is cumulative agent time — the sum of per-attempt durations, not elapsed wall-clock, so a harness that idles between attempts is not penalised here. Two panels, one per model; each is scaled to that model’s own longest run, so the tick ranges differ — compare shape and slope within a panel, not the two panels against each other. Press [ ▶ ] to replay the run at the harness’s own 12 fps.

The scoreboard, attempt by attempt

Every graded attempt as a single dotOne dot per attempt, grouped by model and language, lit when it passed. This is the raw evidence behind the solved counts: it shows which tasks each harness missed, not just how many.

How to read it. A column is one language bucket — JS, PY, RS, C++ — for one model under one harness. Solid dots passed, hollow dots failed. Pass and fail are decided by each task’s own test suite, not by a rubric or a judge model, so a dot here is a test result rather than an opinion.

Output per task

Tokens generated and model calls made, per taskWhat each attempt cost to produce. Two harnesses can reach the same score at very different expense, and that difference compounds over a long run.

How to read it. The tall column is output tokens per task, capped at 2.5k; the short column beside it is model calls per task. Lower is not automatically better — a harness that answers in a single call may simply be guessing — but the pair makes the tradeoff visible: fewer calls at an equal score means less orchestration overhead.

Seconds per attempt, in run order

The spread behind the cumulative curveThe per-attempt wall time for each model, plotted in the order the attempts ran. The race chart shows the total this produces; this shows the distribution that produced it, including the slow tail.

How to read it. Each mark is one attempt: x is attempt number, y is seconds, and the horizontal line is the median. Look at the spread rather than the average. A tight band means predictable latency; a long upper tail means occasional stalls — retries, large files, cold caches — that the cumulative curve hides entirely. A 600 s cap applies per attempt.

Context burned

Cumulative input tokens, cached versus freshInput tokens consumed as the run progresses, split into the part served from the provider’s cache and the fresh part that had to be ingested afresh. This is the cost line that decides whether a long agentic run is affordable.

How to read it. The vertical axis is total input tokens, labelled in k (thousands) or M (millions) depending on the run. Cached tokens are billed cheaply; fresh tokens are paid for in full. A curve whose fresh band stays flat while the total climbs is a harness re-reading its own history instead of re-sending it — good context reuse, visible as a widening gap between the bands.

Cache hit rate

The share of input tokens served from cacheCache behaviour is a property of how a harness orders and reuses its context, which makes it one of the clearest structural differences between these tools.

How to read it. The horizontal axis is progress through the run; the vertical axis is hit rate, fitted to the band actually observed (roughly 50–100%) rather than a full 0–100%, so real differences are visible instead of compressed into the top half. A high, stable line means the prompt prefix is being reused turn over turn. Dips mark the points where context was rebuilt — compaction, reordering, or a fresh session shape.
